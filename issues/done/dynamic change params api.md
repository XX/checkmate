● Проанализировал код. Ниже — анализ текущего состояния и варианты решения.

  Что мешает прямо сейчас

  Два независимых препятствия, и транспорт (сокет/BRP/shm) решает только одно из них:

  1. Параметры «протекают» в компоненты один раз при спавне. Config читается в main() и значения копируются в чужие компоненты: src/main.rs:151 (DirectionalLight/SunDisk/Transform из config.environment.sun),
  src/state/ingame/engine.rs:18 (PointLight + FlickeringLight из jet_fires), AppCameraParams в main.rs:50. После спавна связи «конфиг → сущность» не существует. Часть параметров вообще захардкожена в
  Aircraft::new() / Thrust::new() (src/state/ingame/aircraft.rs:23,50).

  2. Ни один компонент не Reflect и ничего не зарегистрировано (register_type в проекте отсутствует). Из-за этого не работает не только удалённое редактирование, но и уже подключённый WorldInspectorPlugin — он
  показывает только штатные bevy-типы, ваши Aircraft, Thrust, FlickeringLight в нём невидимы.

  Поэтому решение — три слоя, и первый с третьим нужны при любом выборе транспорта:

  [редактор] --транспорт--> [слой параметров: Reflect-компоненты/ресурсы] --apply-системы--> [движковые компоненты]

  Слой параметров + применение (обязательная часть)

  Сделать параметры компонентами на сущности (а не полями глобального Config), тогда редактор адресует их по entity, а применение получается через штатное change detection — то есть бесплатно, когда никто
  ничего не крутит:

  #[derive(Component, Reflect, Debug, Clone)]
  #[reflect(Component)]
  pub struct SunParams { pub illuminance: f32, pub angular_size: f32, pub intensity: f32, pub position: Vec3, pub target: Vec3 }

  fn apply_sun(
      mut q: Query<(&SunParams, &mut DirectionalLight, &mut SunDisk, &mut Transform), Changed<SunParams>>,
  ) {
      for (p, mut light, mut disk, mut tr) in &mut q {
          light.illuminance = p.illuminance;
          disk.angular_size = p.angular_size;
          disk.intensity = p.intensity;
          *tr = Transform::from_translation(p.position).looking_at(p.target, Vec3::Y);
      }
  }

  Стоимость холостого кадра: Changed<T> — это сравнение тиков по уже существующему архетипу из одной сущности, то есть десятки наносекунд. Для ресурсов — .run_if(resource_changed::<Config>). Аналогично
  apply_jet_fire (PointLight/FlickeringLight), apply_camera (Bloom, Exposure, Tonemapping, AtmosphereSettings), apply_aircraft. Все apply-системы — в один SystemSet в PreUpdate, после системы приёма изменений.
                                                                                           
  Отдельно стоит разделить параметры на горячие (мутируются на месте: интенсивность, цвет, скорости, позиция солнца) и структурные (путь к модели, число сопел, shadow_map_size) — вторые требуют пересоздания
  сущности/ресурса, их применять через Commands и только по факту изменения, не пытаясь делать это плавно.

  Плюс register_type::<..>() для всех параметрических типов — это нулевая рантайм-стоимость и заодно чинит инспектор.
                                                                                           
  Варианты транспорта                                                                      
                                                                                           
  A. BRP — bevy_remote (рекомендую как основной)                                           
                                                                                           
  В bevy 0.19 это штатная фича (bevy_remote = ["bevy_internal/bevy_remote"], примеры лежат в examples/remote/). Подключается двумя строками:
                                                                                           
  app.add_plugins((RemotePlugin::default(), RemoteHttpPlugin::default())); // 127.0.0.1:15702
                                                                                           
  Редактор — любой JSON-RPC клиент. Методы (константы в bevy_remote::builtin_methods, строковые значения лучше брать из них, а не хардкодить): BRP_QUERY_METHOD (найти сущность по маркеру Sun),
  BRP_MUTATE_COMPONENTS_METHOD (изменить одно поле по reflect-пути, без пересылки всего компонента), BRP_GET_RESOURCE_METHOD / BRP_MUTATE_RESOURCE_METHOD, BRP_SPAWN_ENTITY_METHOD, BRP_LIST_COMPONENTS_METHOD +
  schema — редактор сам строит UI по схеме типов, без ручной синхронизации.                
                                                                                           
  Производительность: HTTP-сервер живёт в отдельной задаче, в мире выполняется только системa разбора очереди запросов; при пустой очереди — один try_recv. Один запрос — это JSON + reflect-мутация, порядка
  десятков микросекунд; при перетаскивании ползунка это 30–120 сообщений/с, то есть доли процента кадра. Слабое место — не throughput, а то, что при потоковом драге редактор должен слать дельты, а не полное
  состояние сцены.

  B. Горячая перезагрузка конфига (дёшево, дополняет A)

  работу с любым внешним редактором (хоть vim), уже готовые Serialize/Deserialize в src/config.rs. Задержка 100–300 мс, гранулярность — файл целиком (перечитали → сравнили → тронули только изменившиеся поля,
  дальше работает change detection). Как единственный механизм неудобен для ползунков, но как канал «сохранить/загрузить» нужен в любом случае — и в паре с A даёт полный цикл: крутим по BRP, потом одной

  собственный протокол и ручная синхронизация схемы; всё, что BRP даёт даром (discovery, schema, query), придётся писать. Разумен как второй этап, если упрётесь в BRP на потоковых сценариях (драг гизмо,
  запись/воспроизведение сессии).                                                          
                                                                                           
  D. Разделяемая память (пункт из вашего бэклога)

  самый быстрый вариант.                                                                   
                                                                                           
  Но: схема фиксирована и обе программы надо пересобирать согласованно; только плоские данные (никаких String, Vec, спавна сущностей, запросов); нет discovery; нужен unsafe и своя реализация под Windows.
  Поэтому я бы не делал её основным API — только «быстрой полосой» для небольшого набора непрерывно крутящихся чисел, поверх A/B. Практически: на частотах редактора (≤200 Гц изменений) разница между shm и BRP

Горячую перезагрузку конфига пока делать не нужно. А вот возможность сохранить текущие настройки в другой файл конфига - вещь полезная. Как лучше сделать такое сохранение, по какой команде и куда сохранять?

---

● Ключевой момент: источник истины теперь не Config, а компоненты параметров, поэтому «сохранение» — это сбор снимка из мира, а запись файла тут наименьшая часть работы. Отсюда и решения.

  Что сохранять

  Брать за основу ресурс Config (в нём структурные вещи, которых нет в компонентах: пути моделей, presets, log, remote) и переписывать в его копии только те секции, для которых в мире нашлись параметры. Это
  само собой решает проблему состояний: в ангаре нет ни самолёта, ни сопел, ни ландшафта — их секции просто останутся из конфига, а не обнулятся.
  
  Понадобятся обратные преобразования From<&SunParams> for SunSettings и т.д. — зеркало к тем, что уже написаны, плюс Clone на типах настроек.
  
  Рантайм-состояние (Thrust.current/target, позиция самолёта, Movement) в снимок не попадает — оно не параметр.
  
  По какой команде
  
  Один обработчик и два триггера, через сообщение:
  
  #[derive(Message)]
  pub struct SaveConfig {
      /// `None` — путь по умолчанию.
      pub path: Option<PathBuf>,
  }   
  
  1. BRP-метод checkmate.save_config — основной путь для редактора: кнопка «Сохранить» там же, где правятся параметры. Регистрируется без своей инфраструктуры, RemotePlugin это поддерживает:
  
  RemotePlugin::default().with_method_main("checkmate.save_config", save_config_handler)
  
  Метод принимает необязательный path и возвращает фактический абсолютный путь — редактору есть что показать пользователю.
  
  2. Горячая клавиша F5 — для случая, когда крутите значения встроенным инспектором (Backquote) и внешнего редактора нет. Одна система на just_pressed, пишет SaveConfig { path: None }.
  
  CLI-команду добавлять смысла нет: процесс уже запущен, а --config для чтения снимка обратно уже есть.
  
  Куда сохранять
  
  Главное правило: никогда не перезаписывать рабочий Config.toml по умолчанию. Serde-сериализация уничтожит комментарии и закомментированные варианты, которых у вас в конфиге много (альтернативные тонмапперы,
  варианты ландшафта) — потерять их молча неприятно.
  
  Поэтому:

  - по умолчанию — Config.saved.toml в рабочем каталоге, рядом с тем, откуда конфиг читается (from_cwd_and_parents_exists);
  - явный путь из BRP-запроса — пишем куда сказано, включая перезапись Config.toml, если редактор запросил именно это (осознанное действие пользователя);
  - запись атомарная: во временный файл рядом с целевым и rename — иначе падение в момент записи оставит обрезанный конфиг;
  - результат сразу пригоден к запуску: checkmate --config Config.saved.toml.
  
  Из зависимостей нужен toml для сериализации — config умеет только читать. Если позже захочется сохранять в существующий файл с сохранением комментариев и порядка ключей, это делается через toml_edit (правит
  дерево, а не пересобирает файл), но это заметно больше работы, и как первый шаг я бы не брал.
  
  Побочный приятный эффект: Config2.toml, который у вас лежит в корне как ручной эксперимент с частичным конфигом, станет получаться автоматически.
  
  Реализовать по этой схеме?
